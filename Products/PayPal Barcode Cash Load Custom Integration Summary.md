# PayPal Barcode Cash Load Integration — Architecture Summary

## Overview

PayPal (and by extension, Venmo) partners with Green Dot to allow customers to load cash onto their digital wallets at retail locations. The customer receives a barcode (generated by Green Dot) that they scan at the register; the retailer's POS system captures the scan and the funds, and Green Dot routes the transfer back to the PayPal account.

This document covers the three repositories involved and how they fit together.

---

## Repositories

| Repo | Role |
|---|---|
| `GSS-ECHSVC-ECash` | Barcode generation service (internal REST + WCF) |
| `MMGDN-PRT-GDFNPartnerReloadAPI` | Partner-facing intake API; hosts the PayPal OpenWallet endpoint |
| `MMGDN-COM-GDFNPartnerGateway` | POS-side transaction processor; routes funds-in calls back to PayPal |

---

## Request Flow

### Step 1 — Barcode Generation (PayPal → Green Dot)

PayPal calls a dedicated endpoint hosted by Green Dot:

```
POST ~/funding-sources/barcode
Host: MMGDN-PRT-GDFNPartnerReloadAPI
Auth: HTTP Basic (username/password, looked up via PayPalOpenWalletSiteIdentifier = "GDPPCashOpenWallet4App")
```

**Key request fields** (`PayPalBarcodeRequest`):
- `customerDetails.payerId` — PayPal account ID of the recipient
- `customerDetails.name.firstName/lastName`
- `customerDetails.email`
- `customerDetails.billingAddress.postalCode`
- `productDetails.partnerId` — numeric Green Dot retailer key (identifies which retail chain)
- `productDetails.productType` — must be `"CASH-IN"`

**What the controller does** (`BarcodeController.PostPayPalBarcode`):
1. Validates the request fields
2. Validates that `partnerId` is a valid retailer for the **hardcoded** program `PayPal_eCash`
3. Calls `BarcodeManager.GenerateBarcodeNumber()` via internal WCF with:
   - `ProgramNumber = "PayPal_eCash"` ← hardcoded constant
   - `RetailerKey = request.ProductDetails.PartnerId`
   - `Recipient.ExternalAccountId = request.CustomerDetails.PayerId`
   - `BarcodeSource = "PayPalOpenWalletAPI"`
4. Returns the barcode number, expiration, and format (`CODE128`) to PayPal

The WCF call routes internally to `GSS-ECHSVC-ECash`, which generates the barcode number using a DB sequence, applies a Mod10/Luhn checksum, and stores it.

**Important:** The `programCode` is NOT supplied by PayPal — it is hardcoded in the GDFNPartnerReloadAPI controller. PayPal simply calls a fixed URL they were given at integration time.

### Step 2 — Cash Load at Retail (POS → Green Dot → PayPal)

When the customer presents the barcode at a register, the POS terminal sends a transaction to Green Dot's GDFN Partner Gateway (`MMGDN-COM-GDFNPartnerGateway`). The gateway identifies the processor using `ExternalProcessorCode = "PayPal_eCash"` and routes to `PayPalFundsInHandler`.

**PayPalFundsInHandler flow:**
- **Auth** → calls PayPal `POST v2/transfers/deposits-evaluate`; HTTP 204 = approved
- **AuthCommit** → calls PayPal `POST v2/transfers/deposits`; HTTP 200 = settled
- **AuthVoid** → handled locally, no PayPal API call, always returns success

**Auth/AuthCommit request construction** (`PayPalFundsInRequestFactory`):
- `Receiver.Type = "ACCOUNT_NUMBER"` (barcode product type)
- `InvoiceId = "{AccountReferenceNumber}|{SubAccountReferenceNumber}"`
- `CustomData = "MP ref {barcodeNumber}"`
- `StoreId = "{merchantId}:{storeNumber}"`

PayPal uses the `payerId` (stored during barcode generation) to credit the correct wallet account.

## Key Hardcodings

The following values are compiled constants in `MMGDN-PRT-GDFNPartnerReloadAPI`:

| Constant | Value | Location |
|---|---|---|
| `PaypalProgramNumber` | `"PayPal_eCash"` | `BarcodeController.cs:54` |
| `PaypalPartnerCode` | `"PayPal_eCash"` | `BarcodeController.cs:55` |
| `PayPalOpenWalletApiBarcodeSource` | `"PayPalOpenWalletAPI"` | `BarcodeController.cs:52` |
| `PayPalOpenWalletSiteIdentifier` | `"GDPPCashOpenWallet4App"` | `AuthenticationManager.cs:13` |

The route `~/funding-sources/barcode` and all four constants above are PayPal-specific. There is no dynamic lookup — the program/partner code is always `PayPal_eCash` regardless of what `partnerId` is passed in the request body.

> **Note:** A dynamic lookup via `PaypalHelper.GetPaypalProgramNumberByPartnerId(request.ProductDetails.PartnerId)` was written but is currently commented out (`BarcodeController.cs:1773`). The infrastructure for config-driven program number resolution exists but is not active.

---

## Retailer Mapping

`PaypalHelper` reads a `PaypalRetailerMapping` config section (JSON array in `appsettings.json`) that maps PayPal merchant IDs to Green Dot retailer keys. This mapping is used for retailer validation only — it does not currently influence the program number selection.

## Venmo Onboarding Implications

Because the program number is hardcoded to `PayPal_eCash`, onboarding Venmo as a distinct program requires code changes in `MMGDN-PRT-GDFNPartnerReloadAPI`. Two approaches:

### Option A — New dedicated endpoint (mirrors Uber precedent)
- Add `VenmoOpenWalletSiteIdentifier` constant to `AuthenticationManager.cs`
- Add a new `PostVenmoBarcode` action on a new route (e.g., `~/funding-sources/venmo-barcode`) with `VenmoProgramNumber = "Venmo_eCash"` constants
- Add a new `PartnerProfile.VenmoWallet` case in `PartnerProfile.cs`
- Add a DB credential record for the Venmo site identifier
- No changes needed in `GSS-ECHSVC-ECash` or `MMGDN-COM-GDFNPartnerGateway`

### Option B — Activate the dynamic lookup (cleaner long-term)
- Uncomment/implement `PaypalHelper.GetPaypalProgramNumberByPartnerId()` to drive program number from config
- Populate `PaypalRetailerMapping` with both PayPal and Venmo `partnerId → programNumber` entries
- Generalize retailer validation and site identifier lookup to also be config-driven
- Eliminates per-partner code changes for future wallets

Option A is lower risk and consistent with how Uber was added. Option B is the right architectural direction for multi-wallet scalability.
